# Учебная АТС на SIP (`sip_pbx`) — спецификация

Дата: 2026-11-03. Статус: согласована с заказчиком, ожидает финального ревью.
Постановка: SIP-АТС — регистрация телефонов (REGISTER), вызов на зарегистрированного
абонента (INVITE), разговор и отбой (BYE), отмена до ответа (CANCEL), понятный отказ
на незарегистрированный номер. Голос идёт напрямую между телефонами; АТС — только
сигнализация. Язык и библиотеки любые; авторизация — наиболее популярный стандарт.

> Примечание: текст задания (`SIP_Ats_hw2.docx`) будет сверен с этим документом,
> когда файл появится в репозитории; обязательные проверки уже перенесены в
> раздел «Приёмка».

## 1. Решения, зафиксированные при уточнении

| Область | Решение |
|---|---|
| Роль АТС | Registrar + stateful SIP proxy (RFC 3261 §16–17), не B2BUA |
| Стек | Elixir 1.19 / OTP 27; **независимый** парсер SIP (sip_phone не трогается как зависимость) |
| Транспорт | UDP, порт 5060 |
| Авторизация | Digest MD5 (RFC 2617 / RFC 3261 §22) на REGISTER и INVITE + антибрутфорс |
| Медиа | RTP phone↔phone мимо АТС; АТС не модифицирует SDP |
| Критерий приёмки | соответствие реальным софтфонам (строгий вариант); sip_phone после доведения до RFC — клиент автотестов сигнальной части (RTP у него нет) |
| Консоль | веб: метрики с псевдографикой, трассировка вызовов, SIP-журнал, алерты, ровно 3 команды управления |
| Терминология | call leg — **плечо вызова** (плечо A/B); доменные термины (INVITE, digest, nonce, CSeq) не переводить |
| Документация | стандарт CLAUDE.md (модули/README/work_log/CLAUDE.md, doctest'ы, mix docs) — часть DoD |

Термины: **AOR** — адрес абонента `sip:NNNN@АТС`; **binding** — регистрация AOR→Contact
с адресом получения; **плечо** — одна сторона вызова в трассировке.

## 2. Обязательные проверки (из задания) и импликации

| Проверка | Ожидаемый результат |
|---|---|
| Регистрация 1001 и 1002 | оба телефона зарегистрированы на АТС |
| Звонок 1001 → 1002 и ответ | вызов доходит, есть двусторонний звук |
| Отбой после ответа | разговор завершается, повторный вызов проходит; повторить с отбоем с другой стороны |
| Отмена исходящего до ответа | второй телефон перестаёт звонить, повторный вызов проходит |
| Вызов на незарегистрированный номер | понятный отказ (напр. 404), без зависшего вызова |

Инварианты, извлечённые из таблицы:

1. **Двусторонний звук** существует только между реальными софтфонами — значит
   АТС обязана корректно форвардить SDP без изменений, а прямизна медиа
   доказывается отсутствием RTP на захвате с АТС.
2. **«Повторный вызов проходит»** после каждого отбоя/отмены — состояние телефона
   и АТС обязано возвращаться в idle: ни одна транзакция, binding-запись или
   диалог не остаются висеть. Это явное требование к транзакционному слою
   (таймеры §17) и к чистке DialogStore, оно покрывается автотестами.

## 3. Не будет сделано (v1)

TCP/TLS/SIPS; out-of-dialog REFER/SUBSCRIBE/MESSAGE (ответ 405); fork на несколько
Contact одного абонента; hot-reload абонентов; запись/коммутация медиа; авторизация
самой веб-консоли (стенд loopback/LAN — ограничение отмечено в README); RTP/SRTP.

## 4. Архитектура

Новое Mix-приложение `sip_pbx/` рядом с `sip_phone/` (тот же стиль: комментарии
по-русски, deps `plug_cowboy` + `jason`, dev: `ex_doc`, `dialyxir`, `credo`).

### 4.1 Поток сообщения и модель процессов

Один UDP-сокет у `Transport` (GenServer, `active: true`, порт `SIP_PBX_SIP_PORT`,
боевая норма 5060). Transport только демультиплексирует:

- **Запрос**: есть server-транзакция на `key(branch, метод, CSeq, sent-by)` →
  отдать ей (ретранслят, дубликат не доходит до логики повторно). Нет → новая
  server-транзакция; внутри неё `REGISTER` терминирует Registrar, остальное — Proxy.
- **Ответ**: клиентская транзакция по branch верхнего Via нашего запроса.

**Транзакция = процесс** (`SipPbx.SIP.TxServer` / `TxClient`, GenServer под
`TransactionSupervisor`, `:temporary`), стейт-машины строго по RFC 3261 §17:
non-INVITE клиентская/серверная, INVITE клиентская/серверная; таймеры A–M честные
(T1=500 мс, T2=4 с, 64·T1). Все константы — из Application env (тест-крючок:
`T1=20 мс`, чтобы таймауты прогонять миллисекундами).

2xx на INVITE транзакцию **не проходит** (§17.1.1.3/§17.2.1): ретранслят 200 OK до
ACK и форвардинг ACK ведёт Proxy/UAS-ядро.

Прочие процессы (`one_for_one`; консоль не должна ронять телефонию):

| Процесс | Ответственность |
|---|---|
| `Location` | ETS-локация AOR → binding (Contact, received IP:port, expiry); sweep 10 с |
| `Auth` | выдача/проверка digest-nonce (stateless HMAC), nc-трекинг, антибрутфорс |
| `Registrar` | логика REGISTER: 200/403/423, снятие по Expires:0 |
| `Proxy` | маршрутизация, Via/Record-Route, DialogStore, CANCEL, коды отказа |
| `CallTracker` | корреляция по Call-ID в плечи с таймингами — источник трассировки |
| `Metrics` | ETS-счётчики + сэмплер 1 с → кольцо временных рядов (1 ч) |
| `Alerts` | правила, состояние активно/подтверждён, бан-лист IP |
| `Web` | Cowboy 8420 (`SIP_PBX_WEB_PORT`): REST + WS + статика консоли |
| `PubSub` | события: `{:sip_log, …}`, `{:call_event, …}`, `{:alert, …}` (Registry) |
| `LogBuffer` | кольцо SIP-журнала, 2000 записей (аналог телефона) |
| `Users` | статический справочник `config/users.exs`: `%{number, password, name}`; по умолчанию 1001/1002 (+1003 незанятый) |

Ядро АТС про консоль не знает — только пишет события в `PubSub`.

## 5. Регистратор, digest, антибрутфорс

REGISTER (UAS, терминируется):

1. Цикл-проверка Via; AOR из Request-URI.
2. Без `Authorization` → `401` + `WWW-Authenticate: Digest realm, nonce, opaque,
   qop="auth", algorithm=MD5`.
3. С `Authorization`: nonce — stateless `base64(ts, src_ip, HMAC-SHA256(secret))`,
   проверка подписи и свежести (5 мин; просрочен → `401 stale=true`); digest
   сверяется с паролем `Users`; `nc` строго растёт на пару (nonce, username) —
   против replay.
4. Неизвестный номер или неверный пароль → `403` (не подсказываем, что именно).
5. Успех → `200 OK` с Contact: `expires = min(запрошенный, 3600)`;
   `expires < 60` → `423` + `Min-Expires: 60`; `Expires: 0` → снятие binding.
   Один binding на AOR (fresh-wins), хранится received IP:port (§5, rport/received)
   и абсолютный expiry.

digest-повтор REGISTER в том же диалоге (Call-ID/From tag, CSeq+1) обязан
приниматься без зацикливания — ECSS-регрессия из sip_phone (work_log §6) проверяется
тестом. INVITE аутентифицируется тем же механизмом до маршрутизации, challenge —
`407`/`Proxy-Authenticate` (§22.2).

**Антибрутфорс**: >10 неуспешных digest с одного IP за 30 с → блок на 15 мин:
пакеты молча дропаются (не кормим 401), алерт `auth_burst`, разблокировка командой
консоли. Глобальный лимит одновременных транзакций → `503`.

## 6. Прокси и сценарии вызова

In-dialog запросы сверяются с **DialogStore** (ETS: Call-ID + теги сторон → плечи,
route set, контакты); новые — auth + Location. Свой Via добавляется с
`received`/`rport`, на ответе срезается. **Record-Route обязателен** — все
in-dialog сообщения (BYE/ACK/CANCEL) идут через АТС, иначе трассировка слепнет
после соединения.

1. **Регистрация 1001/1002** — секция 5.
2. **Звонок 1001 → 1002**: INVITE(+digest) → 100 Trying → Lookup → форвард на
   received-адрес плеча B; ответы спускаются по Via-стеку; плечи A/B в CallTracker.
3. **Разговор**: 200 OK с чужим SDP проходит нетронутым — RTP идёт напрямую
   phone↔phone; ACK по route set. Дальше АТС наблюдатель.
4. **Отбой**: BYE по route set второму плечу → 200 обратно; диалог удаляется из
   DialogStore; трассировка хранит длительность.
5. **Отмена до ответа**: CANCEL матчится на IST INVITE по branch → АТС отвечает
   200 на CANCEL и форвардит его плечу B → B отвечает 487 → 487 спускается плечу
   A (тот — ACK). Гонка CANCEL/200 OK — строго §16.5: если 2xx уже отправлен,
   200 на CANCEL уходит, ACK+BYE — ответственность телефонов.
6. **Незарегистрированный номер**: абонент есть в справочнике, binding истёк →
   `404 Not Found`; нет в справочнике / неверный пароль → `403`; занятость (`486`)
   генерирует телефон, АТС пропускает.

**Матрица отказов**: `400` битый запрос · `403` auth · `404` нет абонента/binding ·
`405` чужой метод · `407` вызов без digest · `408` плечо B не ответило (таймер F) ·
`481` BYE/CANCEL в несуществующий диалог/транзакцию · `503` лимит транзакций ·
`500` внутренняя ошибка. Каждый отказ — событие журнала и метрик.

**Идемпотентность**: дубликаты INVITE/ACK/BYE схлопываются транзакциями и
DialogStore; повторный INVITE на плечо в `proceeding/ringing` не порождает второй
звонок (регрессия work_log sip_phone §9).

**Политики совместимости**: магический cookie `z9hG4bK` на входящих не проверяется;
сами генерируем только с cookie.

## 7. Веб-консоль (8420)

Cowboy + WS + статика (чистый JS/canvas, тёмная/светлая тема, как `priv/static`
телефона; доступ без auth — ограничение стенда, см. §3).

- **Дашборд**: sparkline-ряды (пакеты in/out, активные диалоги, зарегистрированные,
  ретрансляции/с, CPU/память BEAM, транзакции); плитки состояния; панель алертов
  (активные/подтверждённые) и бан-лист IP. Правила: `auth_burst`, `reg_failure`,
  `tx_timeout_rate`, `retrans_spike`, `beam_mem`, `blocked_ip`; порога в конфиге,
  дребезг, состояние активно/подтверждён.
- **Трассировка вызовов**: список (номера, статус ringing/active/canceled/failed+код,
  длительность) → развёртка по плечам с таймингами состояний; подсветка аномалий
  (задержки, ретрансляты, «диалог умер без BYE»).
- **Журнал SIP**: лента in/out/info с разворотом сырого сообщения, фильтры,
  история из LogBuffer при открытии.
- **Команды (ровно 3)**: снять абонента с регистрации; разблокировать IP;
  принудительно завершить зависшую транзакцию.

События — только через PubSub; состояние доразгружается REST'ом
(`/api/state`, `/api/calls`, `/api/calls/:id`, `/api/alerts`, `/api/blocked`).

## 8. Тестирование

**Юнит** (без сети): парсер — doctest'ы (start-line, компактные имена §7.3.3,
параметры, канонический регистр, битые → `{:error, _}`); digest — векторы RFC 2617
§3.5; транзакции — стейт-машины при `T1=20 мс`: число ретранслятов, F→timeout,
схлопывание дубликатов, 2xx мимо транзакции, матчинг CANCEL.

**Интеграционные** (`async: false`, свои порты из `config/test.exs` — практика
sip_phone §17 work_log; скриптованный Elixir UAC в test-support):

1. REGISTER: 401 → digest → 200 (для 1001 и 1002), binding виден в `/api/state`.
2. digest-повтор REGISTER в том же диалоге без зацикливания.
3. 403 неизвестному номеру; 403 с неверным паролем.
4. `Expires: 0` — снятие; следующий INVITE на снятого → 404.
5. 423 при expires < min.
6. INVITE 1001→1002: 407 → повтор, 100/180/200/ACK, active.
7. BYE A→B и B→A: диалог удалён, повторный вызов проходит (инвариант задания).
8. 481 на BYE в неизвестный диалог.
9. CANCEL: 200 на cancel, 487 плечу B, состояние A свободно, повторный вызов
   проходит; отдельно гонка CANCEL/200 OK.
10. 404 на 1003; 405 на SUBSCRIBE; 400 на мусор.
11. 408 на мёртвый порт (мёртвый binding).
12. Ретранслят INVITE → один звонок; потеря ACK → ретранслят 200 OK.
13. Брутфорс: N×401 → бан (дроппается трафик) → алерт → разблокировка командой.
14. Консоль: `/api/state`, WS-события, страница трассировки, журнал.

**Ручная приёмка софтфонами** (чек-лист в README): строки §2 дословно + «голос есть,
на захвате с АТС RTP не видно» + алерт/бан после перебора паролей. Абоненты —
1001/1002, незарегистрированный — 1003.

**Автоматический контур проверки инварианта «без зависшего вызова»**: после каждого
отбоя/отказа — ассерт пустого реестра транзакций и DialogStore.

## 9. Доведение sip_phone до RFC (отдельная задача, выполняется раньше)

Спецификация правок телефона живёт в его собственном репозитории:
`sip_phone/docs/superpowers/specs/2026-11-03-sip-phone-rfc-hardening.md`
(cookie в BYE, таймеры §17, route set, 423, поборки). Работы по ней начинаются
до реализации АТС; автотесты сигнальной части АТС используют уже исправленный
телефон как тестовый клиент, базовые интеграционные тесты АТС — свой
скриптованный UAC и от телефона не зависят. RTP в sip_phone не добавляем
(условие: сигнальный клиент).

## 11. Риски

| Риск | Митигция |
|---|---|
| Транзакционный слой сложен, гонки (CANCEL/ACK/ретрансляты) | стейт-машины по таблицам §17, тесты с T1=20 мс, тесты гонок отдельными сценариями |
| Строгость разных софтфонов отличается | политика «на входящих не придираемся» (cookie, компактные имена); приёмка минимум двумя софтфонами |
| Утечки процессов транзакций при флуде | `:temporary` + лимит транзакций → 503 + алерт |
| Потеря синхронности документации | гейт DoD + правило «док в том же коммите» |
